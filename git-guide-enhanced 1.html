How Git works

Five minutes here will save you hours of confusion later. Every strange Git error makes sense once you know these four places your code can live.

The four areas Core idea

Working directory→Staging area→Local repository→Remote
  • Working directory — the files you actually see and edit in your folder.
  • Staging area (index) — a holding pen. git add puts changes here. Nothing is permanent yet.
  • Local repository — git commit writes the staged snapshot into history, stored in the hidden .git folder on your machine.
  • Remote — GitHub, GitLab, Azure DevOps. git push uploads your commits there; git pull brings other people's down.

Commits move left to right. Undo commands move things right to left. When you are stuck, ask yourself: which of these four places is my change currently in? The answer tells you which command you need.

Why staging exists: it lets you commit only some of your changes. You fixed a bug and also reformatted a file — stage and commit them separately so the history stays readable.

Words you will keep seeing Glossary

TermWhat it actually means
repoA folder with a .git subfolder in it. That subfolder is the entire history.
commitA permanent snapshot of your staged files, with a message, an author and a unique hash like a1b2c3d.
HEADA pointer to where you are right now — normally the tip of your current branch.
HEAD~1One commit before HEAD. HEAD~3 is three back.
branchA movable label pointing at a commit. Creating one is instant and costs nothing.
mainThe conventional name of the primary branch. Older repos call it master.
originThe default nickname for the remote you cloned from. It is just a name, not a keyword.
upstreamTwo meanings: the remote branch your local branch tracks, or (in forks) the original project you forked.
tracked / untrackedTracked files are ones Git already knows about. New files are untracked until the first git add.
stagedMarked to go into the next commit.
detached HEADYou checked out a commit rather than a branch. Commits made here belong to no branch and are easy to lose.

How to read the commands in this guide Conventions

  • Anything inside angle brackets is a placeholder you replace, e.g. <branch>, <commit-hash>. Do not type the brackets.
  • Grey lines starting with # are comments. You can paste them; the shell ignores them.
  • Blue lines are the commands. Hover any block and press Copy to take the whole thing.
  • Badges mark difficulty: Basic Intermediate Advanced Destructive.
  • Press / or Cmd/Ctrl + K anywhere to search every command on this page.

A suggested path through this guide Instructions

  1. Setup — configure your name and email once, then check they took effect.
  2. Local → GitHub — get the code on your laptop onto a remote, with or without a browser.
  3. Daily basics — status, add, commit, push, pull. This is 90% of normal use.
  4. Branches — as soon as you work with anyone else, or on more than one thing at once.
  5. Conflicts and Undo — read before you need them, not during the panic.
  6. Rewrite history, Advanced tools, Combos — when the basics feel automatic.

The three rules that prevent most disasters Safety

  • Commit early, commit often. A committed change can almost always be recovered. An uncommitted one often cannot.
  • Never rewrite shared history. Rebase, amend and force-push are fine on your own branch, catastrophic on main.
  • Dry-run destructive commands. git clean -nd before git clean -fd; git stash before git reset --hard.
The panic button: git reflog lists every position HEAD has held for roughly the last 90 days. Lost commits, deleted branches and botched rebases are nearly always recoverable from it. See Undo & recover.
Initial setup

Setup

One-time configuration, plus how to check what is actually set.

Tell Git who you are Basic

Your name and email are stamped into every commit you make. Set them before your first commit, otherwise Git either refuses or guesses from your system hostname.

git config --global user.name "Your Name"git config --global user.email "you@example.com"

View what is currently set Basic

This is the part most guides skip. There are three levels of config and the more specific one always wins.

# Show just your name / just your emailgit config user.namegit config user.email# Explicit form — identical result, works in scriptsgit config --get user.name# Show EVERY setting in effect right nowgit config --list# Same, but showing which file each value came from — the useful onegit config --list --show-originIf nothing prints, that key is not set anywhere.
# Check one specific levelgit config --global --get user.name# Repo-only value (run inside the repo)git config --local --get user.name# Machine-wide value, set by an admin or installergit config --system --get user.name# Which config file would --global write to?git config --global --edit
LevelApplies toStored in
--systemEvery user on the machine/etc/gitconfig
--globalYou, in every repo~/.gitconfig
--local (default)This repo only.git/config
Local overrides global. Use a work email on work repos by running git config user.email "you@company.com" (no --global) inside that repo. Verify with git config --show-origin --get user.email — it prints the winning value and the file it came from.

Change or remove a setting Basic

# Overwrite — just set it againgit config --global user.name "New Name"# Delete a single settinggit config --global --unset user.name# Delete a whole section, e.g. all aliasesgit config --global --remove-section alias# Open the config file in your editor and edit by handgit config --global --edit
Changing your email does not rewrite past commits. Old commits keep the old author. To fix the author on the last commit use git commit --amend --author="Name <email>" --no-edit; for many commits see Rewrite history.

Check your Git version and where it lives Basic

git --versionwhich git# Built-in help for any commandgit help commitgit commit -hSome commands here need a recent Git: switch/restore need 2.23+, zdiff3 needs 2.35+.

Sensible defaults worth setting once Intermediate

# New repos start on "main" instead of "master"git config --global init.defaultBranch main# git pull rebases instead of creating merge bubblesgit config --global pull.rebase true# Push only the current branch, and only when it is safegit config --global push.default simple# Show the common ancestor inside conflict markers - far easier to resolvegit config --global merge.conflictstyle zdiff3# Remember how you resolved a conflict and reuse it next timegit config --global rerere.enabled true# Prune deleted remote branches on every fetchgit config --global fetch.prune true# Your editor for commit messages and interactive rebasegit config --global core.editor "code --wait"# Colour outputgit config --global color.ui auto

Aliases that save real time Intermediate

git config --global alias.st statusgit config --global alias.co checkoutgit config --global alias.br branchgit config --global alias.last "log -1 HEAD --stat"git config --global alias.lg "log --oneline --graph --decorate --all"git config --global alias.unstage "restore --staged"# List the aliases you have definedgit config --get-regexp ^alias\.git lg now gives you a visual branch graph in one keystroke.

Authentication: HTTPS or SSH Basic

# Generate an SSH key (press Enter through the prompts)ssh-keygen -t ed25519 -C "you@example.com"# Copy the PUBLIC key and paste it into GitHub > Settings > SSH keyscat ~/.ssh/id_ed25519.pub# Test itssh -T git@github.com# Or let GitHub CLI do all of itgh auth login# Cache HTTPS credentials insteadgit config --global credential.helper store
HTTPS vs SSH: HTTPS asks for a personal access token on every push unless a credential helper is configured. SSH uses a key and never prompts. Switch an existing repo with git remote set-url origin git@github.com:user/repo.git.

Start a new repo on your machine Basic

# Navigate into your project folder first, then:git init# Or init and name the first branch main in one go (Git 2.28+)git init -b main# Confirm it workedgit statusgit init creates a hidden .git folder. That folder IS the repository - delete it and you are back to an ordinary folder.

Clone an existing repo Basic

# Downloads the repo into a new foldergit clone https://github.com/username/repo-name.git# Clone into a folder with a different namegit clone https://github.com/username/repo-name.git my-folder# Shallow clone - only the last 50 commits. Much faster on huge reposgit clone --depth 50 https://github.com/username/repo-name.git# One branch onlygit clone --single-branch --branch develop <url>
After cloning you already have a remote called origin pointing at that URL, and your local main already tracks origin/main. No extra setup needed.

Ignore files you never want committed Basic

# Create .gitignore in the repo root, one pattern per line:node_modules/.env*.log.DS_Storedist/# Already committed by accident? Stop tracking it but keep the filegit rm --cached .envgit commit -m "Stop tracking .env"# Why is this file being ignored? Which rule did it?git check-ignore -v path/to/file# List every ignored file in the repogit status --ignored
Warning: adding a secret to .gitignore after committing it does not remove it from history. Rotate the credential, then scrub history — see Rewrite history → Remove a file from all of history.
No remote yet

Local → GitHub

You have code on your laptop and nothing on GitHub yet. Must you open a browser first? No — with GitHub CLI the whole thing stays in the terminal.

Short answer: git itself cannot create a repository on GitHub's servers — it can only talk to a remote that already exists. GitHub CLI (gh) can create it for you, so everything happens from the CLI. Without gh, you create one empty repo in the browser, and every step after that is terminal-only.

The shape of the task Overview

git init→add + commit→create remote→git remote add→git push -u

Steps 1, 2, 4 and 5 are plain Git. Only step 3 — making the empty repository exist on GitHub — needs either gh or the website.

Scenarios

1 — Fully from the CLI, using GitHub CLI Recommended
No browser at all. gh creates the repo, wires up the remote and pushes, in one command.
# One-time: install gh, then authenticategh auth login# In your project foldercd my-projectgit init -b maingit add .git commit -m "Initial commit"# Create the GitHub repo FROM this folder, add origin, and pushgh repo create my-project --private --source=. --remote=origin --push# Confirmgit remote -vgh repo view --web--source=. means "use this local folder", --remote=origin names the remote, --push uploads immediately. Swap --private for --public or --internal.
2 — Let gh ask you the questions Basic
Run it with no flags and choose "Push an existing local repository to GitHub".
gh repo createInteractive prompts for name, description, visibility, .gitignore and licence, then it offers to add the remote and push.
3 — No gh installed: create the empty repo in the browser first Basic
Create it on github.com and do not tick README, .gitignore or licence — an empty repo avoids an immediate conflict. Then:
cd my-projectgit init -b maingit add .git commit -m "Initial commit"git remote add origin https://github.com/username/my-project.gitgit push -u origin mainThe -u flag sets origin/main as the upstream, so future pushes are just: git push
4 — You ticked "Add a README" and now the push is rejected Common trap
GitHub made a commit you do not have locally, so Git refuses. Pull those commits in first, allowing two unrelated histories to join.
! [rejected] main -> main (fetch first)git pull origin main --allow-unrelated-histories# Resolve any conflicts (usually just README.md), thengit push -u origin main# Prefer a clean history and your local files are authoritative?git push -u origin main --forceOnly force-push here because the remote is brand new and nobody else has cloned it.
5 — Your folder is already a Git repo but has no remote
Check first, then attach one.
# List remotes - empty output means none configuredgit remote -v# Add onegit remote add origin git@github.com:username/repo.git# Point an existing remote at a different URL insteadgit remote set-url origin git@github.com:username/new-repo.git# Inspect everything about a remotegit remote show origin# Rename or removegit remote rename origin upstreamgit remote remove origin
6 — "fatal: The current branch has no upstream branch"
The remote exists, but this branch was never linked to a branch on it.
# Push and link in one gogit push -u origin feature/my-branch# Or link to an existing remote branch without pushinggit branch --set-upstream-to=origin/main main# See which local branch tracks whatgit branch -vv# Make Git set the upstream automatically on every first pushgit config --global push.autoSetupRemote true
7 — Folder full of files, no Git, and you want history clean from commit one Best practice
Write .gitignore before the first git add so junk never enters history at all.
cd my-projectgit init -b mainprintf "node_modules/\n.env\n*.log\ndist/\n" > .gitignore# Dry run: see exactly what WOULD be stagedgit add -A --dry-run .git add .git status -sgit commit -m "Initial commit"
8 — Push an existing repo to a brand-new remote, keeping all history
Moving a project between hosts. Everything — branches, tags, history — goes across.
git remote add origin <new-url>git push --all origingit push --tags origin# Mirror clone: an exact copy including all refsgit clone --mirror <old-url>cd repo.gitgit push --mirror <new-url>
9 — Push to two remotes at once (e.g. GitHub + work GitLab)
git remote add github git@github.com:me/repo.gitgit remote add gitlab git@gitlab.com:me/repo.gitgit push github maingit push gitlab main# Or make ONE remote push to both URLsgit remote set-url --add --push origin git@github.com:me/repo.gitgit remote set-url --add --push origin git@gitlab.com:me/repo.gitgit push origin main
10 — Local repo that should become a repo inside an existing one Advanced
You realise the folder belongs in a monorepo. Move it in, history preserved.
# From inside the big repogit remote add small ../small-projectgit fetch smallgit merge small/main --allow-unrelated-historiesFor a true nested project that stays independent, use a submodule instead - see Advanced tools.

Checklist before your first push Instructions

  1. Run git status — do you see files that should never be committed?
  2. Write .gitignore and re-check with git status --ignored.
  3. Confirm your identity: git config --list --show-origin | grep user
  4. Commit, then git log --oneline to confirm the commit exists.
  5. Create the remote (gh repo create or the website).
  6. Push with -u, then git remote -v and git branch -vv to verify the link.
Daily workflow

Daily basics

The cycle you repeat every day, plus the inspection commands that stop you committing the wrong thing.

Working dir→git add→Staging area→git commit→Local repo→git push→Remote

Check what has changed Basic

Run git status constantly. It is free, and it tells you which of the four areas everything is in — including a hint at the command you probably want next.

# Which files changed, staged, or untrackedgit status# Same thing, one line per file - far less noisegit status -s# Line-by-line changes NOT yet stagedgit diff# Line-by-line changes that ARE staged - exactly what the commit will containgit diff --staged# Just file names and +/- countsgit diff --stat# Ignore whitespace-only noisegit diff -w# Compare against a branch or commitgit diff maingit diff HEAD~3 -- src/app.js
<code>git status -s</code> symbolMeaning
??Untracked — Git has never seen this file
A Added to staging (new file)
 MModified, not staged
M Modified and staged
MMStaged, then modified again afterwards
D Deletion staged
R Renamed
UUBoth modified — a conflict

Stage your changes Basic

Staging means telling Git "include these changes in the next commit". Nothing is permanent until you commit.

# One file / several filesgit add path/to/file.txtgit add src/app.js src/utils.js# Everything changed in the repogit add .# Everything, including deletions, from the repo root wherever you aregit add -A# Only files Git already tracks - skips new untracked filesgit add -u# By patterngit add "*.css"# Preview without staginggit add -A --dry-run

Stage only part of a file Intermediate

You fixed a bug and reformatted three functions. Split them into two clean commits without undoing anything.

# Walk through each chunk and choosegit add -p# Menu-driven equivalentgit add -iy = stage this hunk, n = skip, s = split into smaller hunks, e = hand-edit, q = quit, ? = help.

Commit your changes Basic

# Save staged changes with a messagegit commit -m "Add login button to homepage"# Subject plus body (blank line between them)git commit -m "Fix session timeout" -m "Tokens expired 10x too early: ms read as s."# Stage all TRACKED files and commit in one stepgit commit -am "Fix typo in readme"# Open your editor to write a longer messagegit commit# See what you just didgit show --stat-am only stages files Git already tracks - new files still need git add first.
Message convention that scales: imperative mood, ~50 character subject, e.g. fix: reject expired tokens. Prefixes such as feat:, fix:, chore:, docs:, refactor: make history greppable and can drive automatic changelogs.

Push and pull Basic

# Upload your commitsgit push# First push of a new branchgit push -u origin branch-name# Push tags along with commitsgit push --follow-tags# Download AND merge remote changesgit pull# Pull but replay your commits on top - linear history, no merge bubblegit pull --rebase# Refuse to pull if it would create a merge commitgit pull --ff-only

Fetch vs pull — the distinction that prevents surprises Intermediate

git pull is git fetch followed by git merge, run blind. On a busy branch, fetch first and look before you leap.

# Download remote state WITHOUT touching your working filesgit fetch origin# Inspect what landed before accepting itgit log HEAD..origin/main --onelinegit diff HEAD origin/main# Happy? Then merge or rebase it ingit merge origin/maingit rebase origin/main# Fetch everything and delete refs to branches deleted on the remotegit fetch --all --prune

Read the history Basic to Intermediate

git log# Compact, one line per commitgit log --oneline# Visual branch graph - the single most useful log commandgit log --oneline --graph --decorate --all# Last 5, with the files each touchedgit log -5 --stat# Only commits touching one file, following renamesgit log --follow -p -- path/to/file.js# By author, by date rangegit log --author="Anunjay" --since="2 weeks ago"# Find the commit that added or removed a string (the "pickaxe")git log -S "getUserToken" --oneline# Search commit MESSAGESgit log --grep="timeout" --oneline# What changed between two tagsgit log v1.0..v2.0 --oneline# Custom one-line formatgit log --pretty=format:"%h %an %ar - %s"

Who wrote this line, and why Intermediate

git blame path/to/file.js# Only lines 40-60git blame -L 40,60 path/to/file.js# Ignore whitespace and code movement - finds the REAL authorgit blame -w -C -C path/to/file.js# Then read the full reasoning behind that commitgit show <commit-hash># Just one file as it was at that commitgit show <commit-hash>:path/to/file.js

Moving and deleting files Basic

git mv old-name.js new-name.js# Delete the file and stage the deletiongit rm unwanted.js# Keep the file on disk, just stop tracking itgit rm --cached secrets.env# Remove a whole folder from trackinggit rm -r --cached dist/

A safe daily routine Instructions

  1. Start the day: git switch main && git pull --rebase
  2. Branch for the task: git switch -c feature/thing
  3. Work, then git status and git diff before staging.
  4. Stage deliberately with git add -p, commit with a clear message.
  5. Before pushing: git log --oneline -5 to check the history reads well.
  6. git push -u origin feature/thing and open the PR.
Branches & remotes

Branches & remotes

Branches let you work without touching the main code. Remotes are just other copies of the same repo.

A branch is nothing but a movable label pointing at a commit. Creating one copies no files and takes no time — which is why the right answer to "should I make a branch?" is almost always yes.

List and create Basic

# Local branches (* marks the current one)git branch# Include remote branchesgit branch -a# With last commit and tracking infogit branch -vv# Sorted by most recently used - great on a busy repogit branch --sort=-committerdate# Create a branch without switching to itgit branch feature/my-feature# Create AND switch in one stepgit checkout -b feature/my-feature# Modern equivalent (Git 2.23+)git switch -c feature/my-feature# Branch off a specific commit or tag instead of HEADgit switch -c hotfix/v2 v2.0.1

Switch branches Basic

git checkout maingit switch main# Jump back to the previous branch, like cd -git switch -# Check out a branch that only exists on the remotegit switch feature/theirs# Explicit form of the same thinggit switch -c feature/theirs origin/feature/theirs# Look at an old commit without changing any branch (detached HEAD)git checkout <commit-hash>git switch -
Why two commands? checkout did too many unrelated jobs, so Git split it: switch for branches, restore for files. Both old and new forms still work.
Uncommitted changes block a switch when they would be overwritten. Either commit them, git stash them, or discard them with git restore.

Rename a branch Basic

# Rename the branch you are ongit branch -m new-name# Rename another branchgit branch -m old-name new-name# Push the new name and delete the old one on the remotegit push origin -u new-namegit push origin --delete old-name

Merge a branch Basic

# Step 1: switch to the branch you want to merge INTOgit switch maingit pull# Step 2: bring your feature branch ingit merge feature/my-feature# Always create a merge commit, even when fast-forward is possiblegit merge --no-ff feature/my-feature# Only merge if it can fast-forward, otherwise stopgit merge --ff-only feature/my-feature# Collapse the whole branch into ONE commit on maingit merge --squash feature/my-featuregit commit -m "Add my feature"# Preview what a merge would bring ingit merge --no-commit --no-ff feature/my-featuregit merge --abort

A fast-forward happens when main has not moved since you branched — Git just slides the label forward, creating no merge commit. --no-ff forces a real merge commit so the branch remains visible in history.

SituationUse
Feature branch whose context is worth preservingmerge --no-ff
Messy WIP commits nobody needs to seemerge --squash
Your own unpushed branch, want linear historyrebase
Shared branch others have already pulledmerge — never rebase it

Delete branches Basic

# Safe delete - refuses if the branch is not mergedgit branch -d feature/my-feature# Force deletegit branch -D feature/my-feature# Delete on the remotegit push origin --delete feature/my-feature# Which branches are already merged into main?git branch --merged main# And which are not?git branch --no-merged main# Bulk-clean every merged branch except maingit branch --merged main | grep -v "main" | xargs -r git branch -d
Deleted the wrong branch? It is not gone. git reflog still knows the commit — see Undo & recover.

Compare branches Intermediate

# Commits on feature that are not on maingit log main..feature/my-feature --oneline# Commits unique to EITHER sidegit log main...feature/my-feature --oneline --left-right# File differences between the two tipsgit diff main..feature/my-feature# Only what feature added since it diverged - what a PR showsgit diff main...feature/my-feature# Which branches contain this commit?git branch --contains <commit-hash>Two dots = tip to tip. Three dots = since the common ancestor. The difference matters constantly in code review.

Working with remotes Intermediate

git remote -v# Full detail: URLs, tracked branches, what is stalegit remote show origin# List remote branches onlygit branch -r# Delete local refs to branches that no longer exist remotelygit remote prune origin# What does the remote have that I do not?git fetch && git log ..origin/main --oneline# And what do I have that it does not?git log origin/main.. --oneline

Forks and upstream Intermediate

In a fork workflow, origin is your copy and upstream is the original project.

git remote add upstream https://github.com/original/repo.gitgit fetch upstreamgit switch maingit merge upstream/maingit push origin main# Same thing in one command with GitHub CLIgh repo sync

Branch naming that stays readable Instructions

  • feature/short-description for new work
  • fix/issue-123-login-crash for bug fixes
  • chore/bump-deps for maintenance
  • release/v2.1 and hotfix/... for shipping
Best practice: one branch per feature or bug fix, short-lived, rebased on main often. Keep main always deployable and protect it server-side so nobody can force-push to it.
Conflict resolution

Conflicts

Conflicts happen when two people change the same lines. Git stops and asks you to decide. They are normal, not a failure.

What a conflict looks like inside a file

<<<<<<< HEAD (your local changes)
const greeting = "Hello World";
=======
const greeting = "Hi there";
>>>>>>> origin/main (incoming changes)

Delete the three marker lines, leave the final text you want, save the file, then git add it.

Turn on a better view: git config --global merge.conflictstyle zdiff3 adds a third block showing the original text both sides started from. Seeing what each side actually changed makes most conflicts obvious.

The standard resolution loop Instructions

  1. Run git status to list the conflicted files.
  2. Open each one and decide the final content.
  3. Remove every conflict marker.
  4. Stage the resolved file: git add <file>
  5. Repeat for all files, then git status to confirm none remain.
  6. Build and test. A conflict resolved into valid-but-wrong code is worse than the conflict.
  7. Finish: git commit for a merge, or git rebase --continue for a rebase.

Who is "ours" and who is "theirs"? Important

During--ours / --theirs mean
mergeours = the branch you are on; theirs = the branch being merged in
rebaseFlipped. ours = the branch you are replaying onto; theirs = your own commits
cherry-pickours = current branch; theirs = the commit being applied
stash popours = the working tree; theirs = the stashed changes
This trips up everyone. During a rebase, --theirs keeps your work. git status always spells out which operation you are in — read it before choosing.

Scenarios

1 — See which files conflict
git status# Just the conflicted paths, script-friendlygit diff --name-only --diff-filter=U# Show the conflicting hunks onlygit diffFiles listed as "both modified" are the conflicted ones.
2 — Keep the incoming version of a file
You do not care about your local edits to this one file.
git checkout --theirs path/to/conflicted-file.jsgit add path/to/conflicted-file.js# Modern formgit restore --theirs --worktree path/to/conflicted-file.js
3 — Keep your own version of a file
git checkout --ours path/to/conflicted-file.jsgit add path/to/conflicted-file.js
4 — Manually pick lines from each version
Edit the file to the final result, remove every marker, then:
git add path/to/conflicted-file.jsgit commit -m "Resolve conflict in file.js"# Safety check: are any markers left anywhere in the repo?git grep -n "<<<<<<<"
5 — Use a visual merge tool Intermediate
git config --global merge.tool vscodegit config --global mergetool.vscode.cmd 'code --wait $MERGED'git mergetool# Stop it leaving .orig backup files everywheregit config --global mergetool.keepBackup false
6 — Abandon the operation entirely
Whatever you started, there is an escape hatch back to before it.
git merge --abortgit rebase --abortgit cherry-pick --abortgit revert --abortgit am --abort# Nothing else works? Go back to where HEAD was before the operationgit reset --hard ORIG_HEAD
7 — Conflict in the middle of a rebase Advanced
A rebase replays commits one at a time, so you may resolve several conflicts in sequence.
# Fix the files, stage them - do NOT commitgit add path/to/file.jsgit rebase --continue# This commit is no longer needed? Drop it and move ongit rebase --skip# Where am I in the sequence?git status
8 — The same conflict, over and over Advanced
On a long-lived branch you rebase repeatedly and re-resolve identical conflicts. rerere ("reuse recorded resolution") memorises your fix and replays it automatically.
git config --global rerere.enabled true# Resolve once as normal. Next time Git applies it for you.git rerere statusgit rerere diff# Throw away a recorded resolution that turned out wronggit rerere forget path/to/file.js
9 — Resolve a whole merge in favour of one side Advanced
A blunt instrument. Use when one branch is authoritative — regenerating a lockfile, for example.
# Prefer our side for every CONFLICTING hunkgit merge -X ours feature/my-feature# Prefer their side for every conflicting hunkgit merge -X theirs feature/my-feature-X only decides conflicting hunks. The older -s ours strategy discards the other branch entirely - very different, and rarely what you want.
10 — Binary file or lockfile conflict
There is no sensible line-by-line merge. Pick a side, or regenerate the file.
git checkout --theirs package-lock.jsonnpm installgit add package-lock.json# Or declare a merge policy for that path in .gitattributes:package-lock.json merge=ours
11 — "deleted by them" / "deleted by us"
One side edited a file, the other deleted it. Git cannot guess.
# Keep the filegit add path/to/file.js# Accept the deletiongit rm path/to/file.js
12 — Inspect all three versions before deciding Advanced
Stage numbers let you extract each side as a separate file.
# :1 = common ancestor, :2 = ours, :3 = theirsgit show :1:path/to/file.js > base.jsgit show :2:path/to/file.js > ours.jsgit show :3:path/to/file.js > theirs.js# Diff showing how each side diverged from the ancestorgit diff --base path/to/file.js
13 — Conflict when popping a stash
The stash is not dropped automatically if the pop conflicts, so nothing is lost.
git status# Resolve, stage, then remove the stash yourselfgit add <file>git stash drop# Or bail out and keep the stash untouchedgit checkout --theirs . && git reset
Avoid conflicts in the first place: rebase onto main daily, keep branches short-lived, keep commits small, and agree a code formatter so whitespace never conflicts.
Undo & recover

Undo & recover

Almost nothing in Git is truly lost. The trick is matching the right undo to the mistake.

Pick the right undo Start here

What went wrongCommand
Edited a file, want the last committed version backgit restore <file>
Staged something by mistakegit restore --staged <file>
Bad commit message, not pushedgit commit --amend

The three resets Intermediate

All three move the branch label. They differ in what happens to your files.

FlagEffect
--softMoves the pointer. Changes stay staged. Safest.
--mixed (default)Moves the pointer and unstages. Files on disk untouched.
--hardMoves the pointer and wipes working-directory changes. Destructive.
# Undo last commit, keep changes stagedgit reset --soft HEAD~1# Undo last 3 commits, keep all edits as unstaged workgit reset --mixed HEAD~3# Nuke local commits AND local changes back to the remotegit reset --hard origin/main# Reset a single file to a given commitgit reset <commit-hash> -- path/to/file.js
Warning: git reset --hard permanently deletes uncommitted changes — they were never committed, so the reflog cannot bring them back. Run git stash first if there is any doubt.

Fix the last commit Basic

Amend rewrites the commit and gives it a new hash. If you already pushed, you will need git push --force-with-lease — fine on your own branch, never on shared main.

Revert — the safe undo for pushed commits Intermediate

Revert deletes nothing. It creates a new commit applying the inverse changes, so history stays intact and collaborators are unaffected. This is the correct undo for anything already shared.

git revert <commit-hash># Revert a rangegit revert HEAD~3..HEAD# Stage the inverse but let you commit it yourselfgit revert -n <commit-hash># Reverting a MERGE needs the parent number (-m 1 keeps the mainline)git revert -m 1 <merge-commit-hash># Undo a revert - just revert the revertgit revert <revert-commit-hash>

Reflog — the real safety net Advanced

The reflog records every movement of HEAD: commits, checkouts, resets, rebases, merges. Entries survive for roughly 90 days even when no branch points at the commit any more. This is the command that saves people.

Rewrite history

Rewrite history

Rebase, squash, cherry-pick. These produce a readable, reviewable history — and will ruin a shared branch if misused.

The one rule: never rewrite history that other people have already pulled. Rewrite freely on your own unmerged feature branch; never on main, develop or a release branch.

Rebase vs merge Intermediate

MergeRebase
Adds a merge commit, keeps true chronologyReplays your commits onto a new base, linear history
Existing commit hashes unchangedEvery replayed commit gets a new hash
Safe on shared branchesOnly safe on branches nobody else has
Conflicts resolved onceConflicts may repeat per commit (turn on rerere)

Fix the files, stage, continuegit add <file>git rebase --continue# Push the rewritten branch safelygit push --force-with-lease--force-with-lease refuses to overwrite work someone else pushed while you were not looking. KeywordWhat it does
pick (p)Keep the commit as it is
reword (r)Keep the changes, edit the message
edit (e)Pause here so you can amend or split the commit

Cherry-pick — take one commit, leave the rest Intermediate

Copies the changes from a commit onto your current branch as a new commit with a new hash. The classic use is porting a hotfix into a release branch.

Remove a file from all of history Nuclear

You committed a .env, an API key, or a 400 MB video. It has to come out of every commit.

Bisect — find the commit that broke it Advanced
