Initial setup

Setup

One-time configuration before you do anything else.

Tell Git who you are

Your name and email appear in every commit you make.

git config --global user.name "Your Name" git config --global user.email "you@example.com"

Start a new repo on your machine

# Navigate into your project folder first, then: git init Creates a hidden .git folder — this is what makes a folder a Git repo.

Clone an existing repo from GitHub / GitLab

# Downloads the repo into a new folder on your computer git clone https://github.com/username/repo-name.git This creates a new folder named repo-name in your current directory.
Tip: After cloning, you already have a remote called origin pointing to that URL. No extra setup needed.

Connect a local repo to GitHub (if you used git init)

git remote add origin https://github.com/username/repo-name.git git branch -M main git push -u origin main The -u flag sets origin/main as the default, so future pushes just need: git push
Getting "src refspec main does not match any"? You haven't committed yet — run git add . and git commit -m "Initial commit" before pushing. More in the Fix errors tab.
Daily workflow

Daily basics

The cycle you'll repeat every day.

Edit files → git add → git commit → git push

Check what's changed

# See which files have changed, are staged, or are new git status # See the actual line-by-line changes git diff

Stage your changes (git add)

Staging means telling Git "include these changes in the next commit."

# Stage one specific file git add path/to/file.txt # Stage multiple specific files git add src/app.js src/utils.js # Stage ALL changed files at once git add .

Commit your changes

# Save staged changes with a message git commit -m "Add login button to homepage" # Stage all tracked files AND commit in one step git commit -am "Fix typo in readme" -am only stages files Git already tracks — new files still need git add first.

Push to remote

# Upload your commits to GitHub/GitLab git push # First push of a new branch git push -u origin branch-name

Pull from remote

# Download and merge remote changes into your current branch git pull # Pull from a specific branch git pull origin main

See commit history

# Full log git log # Compact one-line-per-commit view git log --oneline
Branches

Branches

Branches let you work on features without touching the main code.

List and create branches

# See all local branches (* = current) git branch # See all branches including remote git branch -a # Create a new branch git branch feature/my-feature # Create AND switch to it in one step (recommended) git checkout -b feature/my-feature

Switch branches

git checkout main # Modern alternative (Git 2.23+) git switch main

Merge a branch into main

# Step 1: switch to the branch you want to merge INTO git checkout main # Step 2: merge your feature branch in git merge feature/my-feature

Delete a branch

# Delete a local branch (after merging) git branch -d feature/my-feature # Force delete (even if not merged) git branch -D feature/my-feature # Delete a remote branch git push origin --delete feature/my-feature
Best practice: Always make a new branch for each feature or bug fix. Keep main clean and stable.
Conflict resolution

Conflicts

Conflicts happen when two people edit the same line. Git asks you to choose which version to keep.

What a conflict looks like inside a file

<<<<<<< HEAD (your local changes)
const greeting = "Hello World";
=======
const greeting = "Hi there";
>>>>>>> origin/main (remote changes)

Delete the marker lines and keep whichever version you want, then save the file.

Scenarios

1 — Keep the remote version of a specific file
You want GitHub's version of one file and don't care about your local changes to it.
# Accept the remote (their) version git checkout --theirs path/to/conflicted-file.js git add path/to/conflicted-file.js git commit -m "Resolve conflict: keep remote version"
2 — Keep your local version of a specific file
You want to keep what you had locally and discard the incoming remote changes for that file.
# Accept your (ours) version git checkout --ours path/to/conflicted-file.js git add path/to/conflicted-file.js git commit -m "Resolve conflict: keep local version"
3 — Manually pick lines from each version
Open the file, edit it to the final result you want, remove all conflict markers, then:
git add path/to/conflicted-file.js git commit -m "Resolve conflict in file.js"
4 — Abandon a merge entirely
You started merging but want to go back to before the conflict happened.
git merge --abort
5 — See which files have conflicts
git status Files listed as "both modified" are the conflicted ones. Resolve each one, git add it, then commit once at the end.
Golden rule: after resolving all conflicts, run git status and confirm there are no more "both modified" files before committing.
Undo things

Undo things

Git makes it safe to undo almost anything — as long as you haven't pushed yet.

Discard changes in a file (not staged yet)

# Throw away unsaved edits in one file (permanent) git checkout -- path/to/file.txt

Unstage a file (undo git add)

# Remove from staging without losing your edits git restore --staged path/to/file.txt

Undo the last commit (keep your changes)

# Move the commit back to staging — edits are still there git reset --soft HEAD~1

Fix a commit message

# Edit the most recent commit message (before pushing!) git commit --amend -m "Corrected commit message"

Stash work in progress

Temporarily shelve changes so you can switch branches cleanly.

git stash # Get them back later git stash pop # See all stashes git stash list
Warning: git reset --hard permanently deletes uncommitted changes. Never run it unless you're certain. When in doubt, use --soft instead.
Troubleshooting

Fix common errors

Paste or type part of the error you're seeing — the matching fix will show up below.

No matching error. Try a shorter keyword like push or merge.

The first-push checklist

Most first-push errors come from skipping one of these steps. Run them in order:

git init→ git add .→ git commit→ git branch -M main→ git remote add origin→ git push -u origin main
error: src refspec main does not match any Very common
error: src refspec main does not match any error: failed to push some refs to 'https://github.com/you/repo.git'
Git can't find a local branch named main. Either your branch is still called master (older Git default), or you haven't made your first commit yet — a branch doesn't technically exist until it has a commit.
1 — Stage and commit your files (makes sure there's something to push) git add . git commit -m "Initial commit" 2 — Rename your current branch to main git branch -M main 3 — Push again git push -u origin main If step 1 says "nothing to commit", that's fine — you already committed (e.g. via the VS Code Source Control panel). Check your branch name anytime with: git branch
Prevent it forever: git config --global init.defaultBranch main — every new repo you git init will start on main.
Updates were rejected — remote contains work you don't have Very common
! [rejected] main -> main (fetch first) hint: Updates were rejected because the remote contains work that you do not have locally.
GitHub has commits you don't — a README/License created on GitHub, or a teammate (or you, from another machine) pushed first. Bring those in, then push.
# Replay your commits on top of what's on GitHub (clean, linear history) git pull origin main --rebase git push If the pull stops with conflicts, fix them (see the Conflicts tab), then run: git add <file> → git rebase --continue → git push
Don't reach for git push --force here — it would delete whatever is on GitHub that you don't have locally.
fatal: refusing to merge unrelated histories
fatal: refusing to merge unrelated histories
You ran git init locally and created the repo on GitHub with a README. The two histories have no commit in common, so Git refuses to join them by default.
# Tell Git it's OK to combine the two histories git pull origin main --allow-unrelated-histories # Resolve any conflicts (often README.md), commit, then push git push -u origin main Next time: create the GitHub repo empty (no README / .gitignore / License) when you already have local code.
error: remote origin already exists
error: remote origin already exists.
You already linked this folder to a remote. Check where it points, then update it instead of adding it again.
# See current remotes git remote -v # Point origin at the correct URL git remote set-url origin https://github.com/username/repo-name.git # …or remove it and add it fresh git remote remove origin git remote add origin https://github.com/username/repo-name.git
fatal: The current branch has no upstream branch
fatal: The current branch feature/login has no upstream branch.
This is a new local branch that GitHub doesn't know about yet. Push it once with -u to link them.
git push -u origin feature/login After this, plain git push / git pull work on this branch.
Prevent it: git config --global push.autoSetupRemote true (Git 2.37+) makes a plain git push set up the link automatically for new branches.
Authentication failed / password authentication was removed
remote: Support for password authentication was removed. fatal: Authentication failed for 'https://github.com/you/repo.git/'
GitHub no longer accepts your account password for Git over HTTPS. Use a Personal Access Token (PAT) as the password, or sign in through a helper.
Option A — GitHub CLI (easiest) gh auth login Option B — Personal Access Token # GitHub → Settings → Developer settings → Personal access tokens # Create a token, then paste it when Git asks for your password Stuck with an old saved password? (Windows) # Control Panel → Credential Manager → Windows Credentials → remove "git:https://github.com" VS Code usually offers a "Sign in with GitHub" browser pop-up — accepting it also fixes this.
Permission denied (publickey)
git@github.com: Permission denied (publickey). fatal: Could not read from remote repository.
Your remote uses SSH (git@github.com:…) but GitHub doesn't recognise any SSH key on this machine.
# 1. Create a key (press Enter to accept defaults) ssh-keygen -t ed25519 -C "you@example.com" # 2. Copy the PUBLIC key and paste it into GitHub → Settings → SSH and GPG keys cat ~/.ssh/id_ed25519.pub # 3. Test the connection ssh -T git@github.com Prefer to skip SSH? Switch to HTTPS: git remote set-url origin https://github.com/username/repo-name.git
fatal: repository not found
remote: Repository not found. fatal: repository 'https://github.com/you/repo.git/' not found
Either the URL has a typo, the repo is private and you're signed in as a different account, or you haven't been given access.
git remote -v Compare the URL character-by-character with the one on GitHub's green "Code" button.
fatal: not a git repository
fatal: not a git repository (or any of the parent directories): .git
Your terminal is in the wrong folder, or this folder was never initialised.
# Where am I? pwd # Move into the project folder… cd path/to/your-project # …or turn this folder into a repo git init
nothing to commit / nothing added to commit
nothing added to commit but untracked files present (use "git add" to track)
You committed before staging. "working tree clean" means everything is already committed — just push.
git add . git commit -m "Your message"
Author identity unknown — Please tell me who you are
*** Please tell me who you are. fatal: unable to auto-detect email address
Git needs a name and email before it can create commits. One-time fix:
git config --global user.name "Your Name" git config --global user.email "you@example.com"
Your local changes would be overwritten by merge / checkout
error: Your local changes to the following files would be overwritten by merge: Please commit your changes or stash them before you merge.
You have uncommitted edits to files that the pull/switch also wants to change. Park them, pull, then bring them back.
git stash git pull git stash pop Or just commit your work first: git add . → git commit -m "WIP" → git pull
hint: You have divergent branches and need to specify how to reconcile them
fatal: Need to specify how to reconcile divergent branches.
Both you and the remote have new commits. Git wants you to pick a default strategy for git pull once.
# Recommended: put your commits on top (linear history) git config --global pull.rebase true # Or: always create a merge commit git config --global pull.rebase false # Then pull again git pull
You are in 'detached HEAD' state
You are in 'detached HEAD' state. You can look around, make experimental changes…
You checked out a specific commit or tag, not a branch. Anything you commit here isn't on any branch yet.
# Just looking? Go back to your branch git switch main # Made commits you want to keep? Put them on a new branch git switch -c my-rescued-work
error: pathspec 'branch-name' did not match any file(s) known to git
error: pathspec 'feature/login' did not match any file(s) known to git
A teammate created the branch on GitHub, but your machine hasn't downloaded the list of branches yet (or there's a typo).
git fetch git branch -a git switch feature/login git switch automatically creates a local branch that tracks origin/feature/login.
File exceeds GitHub's 100 MB file size limit
remote: error: File data/big.zip is 142.00 MB; this exceeds GitHub's file size limit of 100.00 MB
A big file got committed. If it's only in your latest (unpushed) commit, drop it from that commit:
git rm --cached data/big.zip echo "data/big.zip" >> .gitignore git add .gitignore git commit --amend --no-edit git push If the file is buried in an older commit, see Advanced → Scenarios → "Remove a secret or large file from all history". For files you genuinely need, use Git LFS.
.gitignore isn't ignoring a file
.gitignore only affects untracked files. If the file was committed before you added the rule, Git keeps tracking it. Untrack it (your local copy stays):
git rm --cached path/to/file # For a whole folder, e.g. node_modules git rm -r --cached node_modules git commit -m "Stop tracking ignored files"
warning: LF will be replaced by CRLF
warning: in the working copy of 'app.js', LF will be replaced by CRLF the next time Git touches it
Just a warning, not an error — Windows and Mac/Linux use different line endings. Safe to ignore. On Windows, this setting keeps things consistent:
git config --global core.autocrlf true
Automatic merge failed; fix conflicts and then commit
CONFLICT (content): Merge conflict in src/app.js Automatic merge failed; fix conflicts and then commit the result.
Two changes touched the same lines. Nothing is broken — Git is asking you to choose. Head to the Conflicts tab for the full walkthrough.
General rule: read the hint: lines in Git's output — they usually tell you the exact command to run next.

Rewrite history

Rebase & clean history

Rebase replays your commits on top of another branch, giving a straight-line history. Powerful — but it rewrites commit IDs.

Merge vs rebase at a glance

merge → keeps history, adds a merge commit
rebase → rewrites your commits on top, no merge commit
Golden rule of rebasing: never rebase commits that other people have already pulled. Rebase your own feature branches freely; leave shared branches like main alone.

Update your feature branch with the latest main

git switch feature/login git fetch origin git rebase origin/main # During conflicts: git add <file> && git rebase --continue git rebase --skip # drop the current commit git rebase --abort # go back to before you started # Already pushed this branch? Update it safely: git push --force-with-lease

Interactive rebase — edit, squash, reorder, drop

# Rework the last 5 commits git rebase -i HEAD~5 # Or everything since you branched off main git rebase -i main

Git opens a to-do list. Change the word at the start of each line, save, close:

pick a1b2c3d Add login form
squash e4f5a6b Fix typo in login form # merge into previous, edit message
fixup 9c8d7e6 Oops, lint # merge into previous, discard message
reword 1f2e3d4 add validation # keep changes, rewrite message
edit 5a6b7c8 Big mixed commit # stop here so you can amend/split
drop 0d9e8f7 Debug logging # delete this commit
Reorder commits by simply moving the lines up or down in the list.

Fixup commits + autosquash (the tidy way)

Found a bug in an earlier commit on your branch? Tag the fix to it, and let Git fold it in automatically.

git add . git commit --fixup=a1b2c3d git rebase -i --autosquash main Set once: git config --global rebase.autosquash true — then plain git rebase -i handles fixups for you.

Split one big commit into several

git rebase -i HEAD~3 # mark the commit as "edit" git reset HEAD~ # un-commit it, keep the changes git add -p # stage hunk-by-hunk git commit -m "Part 1: model" git add . git commit -m "Part 2: UI" git rebase --continue

Stage part of a file (git add -p)

git add -p path/to/file.js For each hunk: y = stage, n = skip, s = split into smaller hunks, e = edit manually, q = quit.

Move a branch to a different base (--onto)

You branched feature-b off feature-a, but now want it based on main only:

# git rebase --onto <new-base> <old-base> <branch> git rebase --onto main feature-a feature-b

Stacked branches: rebase them all at once

# Rebases the top branch AND moves every branch pointing into the stack git rebase --update-refs main git config --global rebase.updateRefs true Requires Git 2.38 or newer. Check with: git --version

Squash a whole branch into one commit (without interactive rebase)

git reset --soft $(git merge-base main HEAD) git commit -m "Feature: user login"
Recovery

Recovery & reflog

Git almost never truly deletes a commit. The reflog is your safety net — a diary of every place HEAD has pointed.

The reflog

git reflog a1b2c3d HEAD@{0}: reset: moving to HEAD~3 9f8e7d6 HEAD@{1}: commit: Add payment form 5c4b3a2 HEAD@{2}: rebase (finish): returning to refs/heads/feature # Jump back to any point git reset --hard HEAD@{1} Reflog is local only and entries expire (by default after ~90 days for reachable, ~30 for unreachable commits).

Reset modes compared

CommandCommit historyStaging areaYour files
reset --softMoved backKept (staged)Kept
reset --mixedMoved backCleared (unstaged)Kept
reset --hardMoved backClearedOverwritten

Scenarios

Recover a deleted branch Safe
# Find the last commit the branch pointed to git reflog | grep feature/old git branch feature/old 9f8e7d6
Undo a rebase or merge that went wrong Safe
# Right after the operation, Git saves the old position in ORIG_HEAD git reset --hard ORIG_HEAD # Did something else since? Find the pre-rebase entry git reflog git reset --hard HEAD@{5}
Undo a commit that's already pushed Safe for shared branches
Don't rewrite shared history — create a new commit that reverses it.
git revert a1b2c3d # Revert several commits into one revert commit git revert --no-commit a1b2c3d..HEAD git commit -m "Revert feature X"
Revert a merge commit
Merge commits have two parents; -m 1 says "keep the mainline (the branch you merged into)".
git revert -m 1 <merge-commit-sha> Heads-up: re-merging that same branch later won't bring the changes back — you'd need to revert the revert first.
Restore one file from an older commit
git restore --source=a1b2c3d path/to/file.js # Or peek without changing anything git show a1b2c3d:path/to/file.js
Find a dropped stash or orphaned commit
git fsck --no-reflog | grep "dangling commit" git show <sha> git stash apply <sha>
Before any scary command, drop a bookmark: git branch backup/before-rebase. It costs nothing and you can delete it afterwards.
Remotes

Remotes, forks & tags

Working with more than one remote, force-pushing safely, and releasing versions.

--force-with-lease instead of --force

git push --force-with-lease git push --force-with-lease --force-if-includes --force-with-lease refuses to overwrite the remote if someone pushed since your last fetch. --force-if-includes adds protection against a background fetch silently updating your remote-tracking ref.
Never force-push to main or any branch others build on unless the whole team agrees.

Keep a fork in sync with the original

git remote add upstream https://github.com/original-owner/repo.git git fetch upstream git switch main git rebase upstream/main git push --force-with-lease origin main

Check out a GitHub pull request locally

git fetch origin pull/123/head:pr-123 git switch pr-123 Or with GitHub CLI: gh pr checkout 123

Clean up stale remote branches

git fetch --prune # Make it automatic git config --global fetch.prune true # List local branches already merged into main git branch --merged main

Rename a branch (local + remote)

git branch -m old-name new-name git push -u origin new-name git push origin --delete old-name

Switch remote from HTTPS to SSH (or back)

git remote set-url origin git@github.com:username/repo-name.git git remote -v

Tags & releases

# Annotated tag (recommended — stores author, date, message) git tag -a v1.2.0 -m "Release 1.2.0" # Tag an older commit git tag -a v1.1.1 9f8e7d6 -m "Hotfix" git push origin v1.2.0 git push origin --tags # Delete a tag locally and remotely git tag -d v1.2.0 git push origin --delete v1.2.0 # Which tag is this commit closest to? git describe --tags
Moving work around

Stash & cherry-pick

Shuffle changes between branches without messy merges.

Stash like a pro

# Named stash git stash push -m "half-done navbar" # Include untracked (new) files git stash push -u # Stash only specific files git stash push -m "just css" -- src/styles.css # Stash only what's staged (Git 2.35+) git stash push --staged # Inspect git stash list git stash show -p stash@{1} # Apply but keep it in the list (pop removes it) git stash apply stash@{1} git stash drop stash@{1} # Turn a stash into its own branch (great when pop conflicts) git stash branch rescue-branch stash@{0}

Cherry-pick

Copy specific commits from one branch onto your current branch.

git cherry-pick a1b2c3d # A range: A..B excludes A, so use A^..B to include it git cherry-pick a1b2c3d^..f6e5d4c # Record where it came from in the message git cherry-pick -x a1b2c3d # Bring the changes in without committing yet git cherry-pick -n a1b2c3d # On conflict git cherry-pick --continue | --skip | --abort

Scenarios

Committed to main instead of a feature branch (not pushed)
# 1. Create the branch where you are — it keeps the commits git branch feature/oops # 2. Move main back to match GitHub (drops the stray commits from main only) git reset --hard origin/main # 3. Carry on on the feature branch git switch feature/oops
Committed to the wrong existing branch
git log --oneline -3 # copy the sha git switch correct-branch git cherry-pick a1b2c3d git switch wrong-branch git reset --hard HEAD~1
Ship a hotfix from a feature branch to main
git switch main git pull git cherry-pick -x <hotfix-sha> git push
Investigate

Debug & search history

Find out who changed what, when, and which commit broke things.

Readable history

git log --oneline --graph --decorate --all # Commits on feature that aren't on main git log main..feature --oneline # Filter by author, date, path git log --author="Anunjay" --since="2 weeks ago" -- src/ # Full history of one file, even across renames git log --follow -p -- path/to/file.js # Who commits most git shortlog -sn

Search the code & the history

# Search tracked files right now (fast, respects .gitignore) git grep -n "apiKey" # "Pickaxe": commits that added or removed this exact string git log -S "calculateTotal" --oneline # Commits whose diff matches a regex git log -G "timeout\s*=" --oneline

Better diffs

git diff --staged # what you're about to commit git diff main...feature # only changes made on feature since it branched git diff --stat # summary by file git diff --word-diff # great for prose / markdown git range-diff main old-feature new-feature # compare a branch before/after rebase

Blame, but smarter

# Lines 40–60 only, ignore whitespace, detect code moved from other files git blame -w -C -L 40,60 src/app.js # Skip bulk-formatting commits (list their SHAs in the file) git config blame.ignoreRevsFile .git-blame-ignore-revs

Bisect — binary-search for the commit that broke it

git bisect start git bisect bad # current commit is broken git bisect good v1.4.0 # this one worked # Git checks out a middle commit — test it, then answer: git bisect good # or: git bisect bad # Fully automatic: script exits 0 = good, non-zero = bad git bisect run npm test git bisect reset # return to where you started With 1,000 commits between good and bad, bisect needs only about 10 steps.
Scale

Worktrees, big repos & submodules

Work on several branches at once and tame huge repositories.

Worktrees — multiple branches checked out side by side

No more stashing to review a PR or ship a hotfix. Each worktree is its own folder sharing one repo.

git worktree add ../myapp-hotfix hotfix/login # New branch in a new folder git worktree add -b feature/x ../myapp-x main git worktree list git worktree remove ../myapp-hotfix git worktree prune The same branch can't be checked out in two worktrees at once.

Faster clones

# Shallow: only the latest commit (great for CI) git clone --depth 1 https://github.com/org/big-repo.git git fetch --unshallow # get full history later # Partial (blobless): full history, file contents downloaded on demand git clone --filter=blob:none https://github.com/org/big-repo.git

Sparse checkout — only the folders you need

git clone --filter=blob:none --sparse https://github.com/org/monorepo.git cd monorepo git sparse-checkout set apps/web packages/ui git sparse-checkout add docs git sparse-checkout disable # back to everything

Git LFS — large binary files

git lfs install git lfs track "*.psd" "*.mp4" git add .gitattributes git add design.psd git commit -m "Track design files with LFS" Only affects files added after tracking. Moving existing history into LFS: git lfs migrate import --include="*.psd"

Submodules

git submodule add https://github.com/org/lib.git vendor/lib # Cloning a repo that has submodules git clone --recurse-submodules <url> # Already cloned and the submodule folder is empty? git submodule update --init --recursive # Pull latest commits for every submodule git submodule update --remote

Housekeeping

git maintenance start # schedule background optimisation git gc # compress and clean up now git count-objects -vH # how big is .git? git clean -n # preview untracked files to delete git clean -fd # delete untracked files & folders
Warning: git clean -fd is permanent — untracked files aren't in Git, so the reflog can't bring them back. Always run -n first.
Configure

Config & aliases

A few settings that prevent most everyday errors and save a lot of typing.

Recommended global settings

# New repos start on main (prevents "src refspec main does not match any") git config --global init.defaultBranch main # First push of a new branch sets upstream automatically (Git 2.37+) git config --global push.autoSetupRemote true # git pull rebases instead of creating merge commits git config --global pull.rebase true # Auto-stash dirty changes before a rebase, re-apply after git config --global rebase.autoStash true # Fold fixup! commits automatically in rebase -i git config --global rebase.autosquash true # Remove deleted remote branches on every fetch git config --global fetch.prune true # Conflicts also show the original "base" version — much easier to resolve git config --global merge.conflictstyle zdiff3 # Remember how you resolved a conflict and reuse it next time git config --global rerere.enabled true # Show the diff in the commit message editor git config --global commit.verbose true zdiff3 needs Git 2.35+. On older Git use diff3.

Aliases

git config --global alias.st "status -sb" git config --global alias.lg "log --oneline --graph --decorate --all" git config --global alias.undo "reset --soft HEAD~1" git config --global alias.amend "commit --amend --no-edit" git config --global alias.pushf "push --force-with-lease" Now: git st, git lg, git undo, git amend, git pushf

Separate work & personal identities

Use a different email automatically for repos under a given folder. In ~/.gitconfig:

Push rejected after you rebased or amended your own branch
! [rejected] feature -> feature (non-fast-forward)
Expected — you rewrote commits the remote already had. If the branch is yours alone:
git push --force-with-lease If it says "stale info", someone else pushed. Run git fetch, inspect with git log HEAD..origin/feature, rebase onto it, then push again.
A teammate force-pushed and your local branch diverged
# No local work you care about? Match the remote exactly git fetch git reset --hard origin/feature # Have local commits to keep? Replay only yours onto the new remote git rebase --onto origin/feature <old-remote-sha> feature Find <old-remote-sha> with: git reflog show origin/feature
PR was squash-merged, now the branch looks diverged
After a squash merge, your branch's commits aren't in main by ID. Don't keep building on it — start fresh.
git switch main git pull git branch -D feature/old git switch -c feature/next
Resolving the same conflict over and over during rebases
git config --global rerere.enabled true "Reuse recorded resolution" — Git remembers how you fixed a conflict and applies it automatically next time.
Stuck mid-rebase and not sure what's going on
git status # shows which commit is being applied git diff --name-only --diff-filter=U # list conflicted files git rebase --abort # bail out completely, nothing lost

git restore --source=feature/redesign -- src/theme.css
! [remote rejected] shallow update not allowed
You pushed from a shallow clone (--depth) to a new remote that needs full history.
git fetch --unshallow git push
Protected branch — push declined
remote: error: GH006: Protected branch update failed for refs/heads/main.
The repo requires changes to go through a pull request. Move your commits to a branch and open a PR:
git switch -c fix/my-change git push -u origin fix/my-change git switch main && git reset --hard origin/main
error: RPC failed / early EOF on a big push or clone
error: RPC failed; HTTP 400 curl 22 The requested URL returned error: 400
Usually the push is too large in one go or the connection is flaky. Try pushing in smaller chunks, or switch to SSH.
git config http.postBuffer 524288000 # Push history in pieces (oldest commits first) git push origin <older-sha>:refs/heads/main If large binaries are the cause, move them to Git LFS instead.
fatal: Unable to create '.git/index.lock': File exists
A previous Git command (or your editor) crashed mid-operation. Make sure no other Git process is running, then:
rm .git/index.lock Windows PowerShell: Remove-Item .git\index.lock
Renamed a file's capitalisation and Git ignores it
Windows and macOS file systems are case-insensitive by default, so readme.md → README.md isn't detected.
git mv readme.md README.md git commit -m "Rename readme to README"
